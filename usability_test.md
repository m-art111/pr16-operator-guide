# Испытание руководства

## Режим испытания

**Аналитическое испытание по модели интерфейса.** Стенд с работающим сервисом не предоставлен, поэтому проверка проводилась по тексту руководства и описанию интерфейса `data/operator_observations.md` (версия 1.5.0). Для каждого шага руководства проверялось, существует ли названный элемент и ожидаемый переход в описании интерфейса.

| Параметр | Значение |
|---|---|
| Объект проверки | `history/operator_guide_v1.md` (редакция 1) |
| Модель интерфейса | `data/operator_observations.md` |
| Эталон правил | `data/service_spec.md` (SPEC-1.0) |
| Участники | Редакция 1 — аналитический проход одним проверяющим (разделы 1–3). Редакция 2 — проход партнёра, получившего только руководство и описание интерфейса (раздел 5) |
| Учётные записи | Не использовались (нет стенда) |

**Ограничения проверки**

- Режим обнаруживает пропуски и неоднозначности текста, но **не подтверждает реальное поведение приложения**. Ни один шаг не выполнялся в настоящем сервисе; колонка «Наблюдение» содержит результат сверки с моделью, а не действия пользователя.
- Замечания З-01…З-30 и П-01…П-04 получены при проверке одним человеком. Партнёр проверял уже исправленную редакцию 2 и тоже по модели интерфейса, без стенда (раздел 5).
- Готовые наблюдения O-01, O-02, O-03 из `operator_observations.md` использованы как описание того, как интерфейс ведёт себя по условию кейса, а не как действия при испытании.

## 4. Вопросы для будущего читателя и для проверки на стенде

1. Понятно ли, как открыть карточку из списка «Заявки»? (В модели способ не описан — В-1.)
2. Какое сообщение появляется при пустой теме, слишком длинном описании, файле не того типа или размера? (В-3, В-4.)
3. Хватает ли шагов сценария 3, чтобы не создать дубль, если ответ не пришёл дважды?
4. Видит ли техник после «В работу» кнопку «Отметить выполненной» сразу, без обновления страницы?
5. Каким способом в организации принято обращаться в поддержку? (В-6.)
